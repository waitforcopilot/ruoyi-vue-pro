## 4. FA-01 代码路径

当前 `dependencies()` 第 44 行对本项目的需求、工作台节点、授权和决议做了项目限定，但 `roots`、`anchors` 调用 `store.all(null, …)`，`users` 来自 `userFacts()`。`Store.all` 第 31 行使用 `eqIfPresent`；`LambdaQueryWrapperX.eqIfPresent` 在值为空时不加该条件。`lockUserFacts` 的 SQL 是 `SELECT id,nickname,status FROM system_users WHERE deleted=0 ORDER BY id FOR UPDATE`。该报告没有据此宣称租户拦截被绕过，这个保留成立。

预检查把该集合摘要写入 `dependencyToken`（第 81 行）。正式发布在第 89 行先要求请求令牌等于当前摘要，第 90 行才按幂等号返回已有 release。因此，同租户另一项目新增或签署 ROOT，或全局未删除用户事实变化，都可能让本项目预检查后的首次提交和同号重试在命中旧结果之前失败。幂等测试 `publishAndRetriesRequireCurrentRootAndExactDependencyAndRequest` 在第 82 行，覆盖稳定依赖下的重复请求、同号改文和撤销后拒绝，没有覆盖“本项目依赖不变、仅另一项目新建无关 ROOT”。

PRD 第 8.3 节写明：决议变更先提交时，旧发布请求拒绝并重取当前依赖。该报告要求保留这条边界，与 PRD 原文一致。

补充一点，不改变 FA-01 的定级。真正写入快照的根是 `store.all(项目, "ROOT")`，锚点是 `projectId=0` 的 ANCHOR 再按这些根的 `anchorId` 过滤；快照里的 `userFacts` 随后又收窄到本快照相关人员。依赖令牌比最终冻结快照更宽。影响仍是错误冲突和额外重试，本复核同样没有做跨项目部署复现，不能把它升成已证实的越权发布或数据泄露。
