## 4. 逐一修复建议与恢复验收条件

### R1：P0，修复首次定薪默认项目与后端口径不一致

实际反例：定薪申请包含基本工资6000及多项0值项目，其中包括应发、应税、个税、实发和累计结果项。HR复核可通过，财务应用时报错。详情证据并非仅输入一个6000的推测。

代码对应：

- `SalaryEmployeeInfoForm.vue:280` 只按非根分类和 `calculateEnabled` 过滤，计算结果项也进入默认表单；`getSelectedOptionDefinitions`（387行）在无模板时使用此清单。
- `HrmSalaryEmployeeInfoServiceImpl.java:790` 用 `getSalaryOptionList(true)` 作为审批应用的允许清单；`HrmSalaryOptionServiceImpl.java:171` 对可调薪分类范围再过滤。
- `HrmSalaryEmployeeInfoServiceImpl.java:750` 遇到清单外代码即报“薪资数据不合法”；`HrmPayrollSalaryProposalService.java` 在提交时保存快照，到财务审批才应用。

以上是页面反例与源码相互支持的根因判断，未通过运行时断点逐个确认被拒的代码。建议统一前后端“可定调薪”定义，默认和模板都只提供合法定额项目；计算项保留为核算结果，不能靠全部填0绕过。提交申请时即校验项目代码、金额和适用性，返回具体项目原因，避免无效申请走到财务。

恢复标准：同一员工重新申请基本工资6000，页面只提交允许项目；由不同三人提交/复核/批准后，在薪资档案和生效记录中看到6000。另验证非法项目在提交时明确拒绝，审批期间项目失效仍有防御校验，不能用放宽后端白名单解决。

### R2：P0，修复定薪弹窗模板初始化

实际反例：列表已显示“浏览器流程基本工资模板”，但定薪下拉“无数据”；刷新和关闭重开均复现。不能把“模板不存在”作为用户配置问题。

代码线索：`SalaryEmployeeInfoForm.vue:226` 打开弹窗后立即 `loadSimpleData`，283行以可选调用 `templateSelectRef.value?.init()` 初始化子组件；`Dialog.vue:97` 开启 `destroy-on-close`，子组件挂载前调用可能被静默跳过。`SalaryChangeTemplateSelect.vue` 没有自行挂载加载，依赖父组件调用 `init`。**生命周期是待修复验证的根因线索，不把静态推断当运行时定论。**

建议将模板请求放入父组件统一加载，向下传列表；或在弹窗内容挂载后可靠初始化并显式处理失败。区分加载中、加载失败和真正空列表，新建模板后能刷新选择；不得把加载失败静默降级为“全部薪资项”。

恢复标准：首次打开、关闭重开、整页刷新、新建模板返回四条路径均能选择正确模板，选中后只显示基本工资，成功重提并完成 R1 的三人批准。

### R3：P2，明确主体配置入口并保留操作上下文

实际观察：主体批准后操作列为空，点击整行才出现新增人员归属/授权。功能存在；撤回早期“入口缺失”的判断。

建议增加“人员归属/配置”明确入口或提示，保存和刷新后保留当前主体；避免操作者以为主体批准后无可继续步骤。源码位置 `views/hrm/payroll/entity/index.vue:8` 的 `current-change` 与34行 `v-if="selected"`。

恢复标准：首次进入能找到归属配置，保存后仍在原主体上下文；入口变化不扩大授权。

### R4：P1，补充前置状态提示，排在定薪阻断修复之后

税务政策未批准时年度档案提交被拒，这是合理的前置拦截，本轮不认定校验本身错误。可以在档案按钮旁明确显示“先批准该主体年度政策”及跳转，代替提交后泛化的政策/金额/主体错误。批次0人时同样提示先检查批准归属；本轮没有充分证据认定空批次核算已经错误成功。

恢复标准：前置未就绪时，用户能从页面直接定位缺项；满足条件后原表单可继续，具体错误和数据不丢失。

**R1/R2 → 同一员工定薪批准 → T4员工缴费/税务资料 → T5输入与复核 → T6试算核对 → T7审批冻结 → T8模拟代发回盘 → T9本人工资条 → T10报表对账归档。**
