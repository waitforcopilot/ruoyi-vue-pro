## F-01：MySQL 租户 SQL 与行锁（已修复并运行验证）

JSqlParser 4.9 在租户/数据权限重写后把行锁放到 ORDER BY、LIMIT 前。新增最后执行的 SQL 拦截器，以 AST 访问器将每层 SELECT 的锁放回该层尾部，保留租户谓词、绑定参数、NOWAIT/SKIP LOCKED 和嵌套查询。继续使用 JDK 8，不取消租户和行锁。

验证：4 项序列化测试、1 项真实 MySQL 集成测试全部通过。MySQL 测试实际执行排序及 LIMIT 查询，确认租户 2 的行不可见；持锁时另一连接修改本租户选中行返回 1205，事务结束后清理测试表。使用环境变量 `HRM_MYSQL_TEST_URL` 启用该集成测试；交付门禁必须设置该变量，不能把默认跳过视为通过。

Cloud 后端重新打包并启动后，真实登录验证 6 个写操作：工资项创建、公式独立审批、薪级创建及独立审批成功，公式和薪级自审均拒绝（1050810005）。见 [运行结果](hrm-prd-remediation-evidence/f01-runtime.json)。本轮复用审计库的隔离目录夹具，不等同于新库核算通过。

独立创建 `hrm_remediation_20261016`，完整迁移及重复升级均成功。租户目录从 0 项经真实 API 同步为 68 项，重复同步内容一致，停用基本工资后再次同步仍保持停用，恢复后可通过正常 API 新增工资项。检查脚本现会检验所有枚举项目、父分类及启用状态。另通过未知路由及模块缺失的服务端测试和真实错误路径回归。证据：[新库运行结果](hrm-prd-remediation-evidence/f02-f05-fresh-runtime.json)。此数据库没有直接写入工资目录夹具；仅复制测试管理员密码散列以便登录。

## F-03：部门/本人范围（已修复并运行验证）

新增 HRM 数据权限规则，将现有主体/操作授权与系统部门、本人数据范围取交集。员工候选、个人源数据、按 ID 查询及更新/删除共用 SQL 过滤；关联历史跟随原记录，带数据文件及无法安全拆分的主体快照在受限范围内拒绝访问。批次必须能证明参与人范围且不含范围外员工，才向受限账号开放，防止通过整批汇总、运行快照、付款及成本记录泄漏金额。规则按员工当前组织及账号绑定判断；已有主体授权和租户限制继续生效。配置规则等共享元数据保持可读。`ALL` 范围继续由既有主体授权控制。

**F-01 补充修复**：真实写入负向测试发现 MP 3.5.17 的 `selectOne` 使用独立 SqlSession 游标，绕过查询阶段数据权限且提前释放锁。公共 `BaseMapperX` 恢复在调用会话中读取，保留单条/重复条数异常语义。新增真实 Mapper + MySQL 租户/事务测试，确认持锁阻断并发更新、回滚后更新成功；此前 JDBC 测试仅证明 SQL 行为，不能单独证明 Mapper 事务正确。

验证：6 项 SQL/真实 MySQL 测试通过；5 项接入真实数据权限拦截器的数据库测试通过，覆盖空范围、全部、部门、本人、单条/加锁读取、越权更新删除、可见独立批次/不可见混合及无参与人批次。Cloud 中两部门真实账号验证金额、缴费明细、员工候选、越权创建、混合批次详情及列表；结果见 [F-03 证据](hrm-prd-remediation-evidence/f03-runtime.json)。新增可重复运行的 `scripts/hrm/runtime_scope_regression.py`；测试角色范围在 finally 中恢复。员工仅用 SQL 准备虚构身份以避免创建通知，主体归属和缴费审批全部通过真实 API。

运行中另发现 LocalDateTime 的 ISO 字符串输入被旧反序列化器静默转换为 0；F-03 批次证据已改用原有毫秒契约重新创建有效期间，日期输入问题纳入 F-09 修复。

## F-09：日期输入/输出契约（已修复并运行验证）

HTTP `LocalDate` 统一输出 ISO `yyyy-MM-dd`，不再展示数组。`LocalDateTime` 继续输出毫秒值并兼容原数字/数字字符串输入，新增 ISO 本地时间、空格分隔时间和带时区 ISO 输入；非法类型及文本不能再静默变为时间戳 0。JSON 参数解析错误返回 400，服务端定义错误仍保留服务器异常处理。月度批次的计薪期间必须与所选月份有交集，继续允许已有跨月工资周期。

HTTP Mapper 与内部快照 Mapper 分离，仅为内部日期保留历史数组表示，避免线上的日期展示变化破坏已有冻结来源摘要。旧日期数组仍可反序列化，毫秒时间兼容性不变。

验证：3 项序列化/兼容测试、2 项 Jackson/MVC 测试、27 项月度工资测试通过。Cloud 实际验证 ISO 期间保存正确、字符串/布尔/小数/对象日期输入均返回 400、期间外的 0 毫秒被拒绝；新公式正常创建并独立批准，接口返回 ISO 有效日期。浏览器确认日期正常显示且无脚本错误。见 [API 结果](hrm-prd-remediation-evidence/f09-runtime.json)、[浏览器结果](hrm-prd-remediation-evidence/f09-browser.json) 和 [截图](hrm-prd-remediation-evidence/f09-formula-dates.png)。回归脚本：`scripts/hrm/runtime_date_regression.py`。

## F-04：需求确认与旧数据修复（已修复并运行验证）

确认需求必须填写字段映射；没有业务数据字段的需求可填写 `不适用：具体理由`。来源及评审负责人须为可访问的有效启用用户，确认操作必须由所选评审负责人本人完成，维护权限继续由接口权限控制。待确认/评审中仍允许收集不完整资料；确认不自动改变数据就绪状态。页面补充字段说明和本人操作提示。

新增第 52 个迁移，将缺映射/明确不适用说明或负责人记录不存在的旧确认退回 `REVIEWING`，清除当前确认标记、增加版本和系统校验历史，保留原确认快照和原依据。迁移不会仅因账号当前停用而追溯撤销历史确认；重新确认时执行有效账号校验。

验证：9 项服务测试通过。通过修复前真实 API 在隔离库复现旧漏洞，迁移连续执行两次后仅生成一个新历史版本。修复后真实接口验证空映射、裸 N/A、不存在/停用负责人、代他人确认全部拒绝且不新增历史；有效确认、不适用理由、重新打开、旧版本冲突、确认与就绪独立均通过。浏览器实际触发表单提示、由本人确认、保存及刷新后仍为“已确认/未就绪”。见 [API 与升级结果](hrm-prd-remediation-evidence/f04-runtime.json)、[浏览器结果](hrm-prd-remediation-evidence/f04-browser.json)、[截图](hrm-prd-remediation-evidence/f04-confirmation-browser.png)。前端运行构建通过。
