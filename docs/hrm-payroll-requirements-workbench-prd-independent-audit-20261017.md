## 1. 审计结论

**可继续作为业务讨论稿；尚不足以直接冻结为研发实施和验收基线。**

本稿对“用业务页面征集功能和数据源需求”的定位清楚，明确保留既有业务能力，并正确区分功能确认、来源可用、实现状态和业务验收。没有发现将原型预置状态直接当成真实确认、将示例政策直接作为生产规则的表述。

但核心业务契约仍存在可产生不同实现结果的缺口：多项目候选编号、共享来源变更后的确认有效性、纳入范围与统计、正式基线发布条件、授权判定、历史导出的关联快照，以及问题闭环。本次提出 **7项问题：P1 4项、P2 3项，无P0发现**。P1表示应在对应能力开发定稿前解决的需求缺陷，不表示已证明生产系统发生事故；P2表示会造成验收歧义或闭环不完整的问题。

目标文件已自行声明“待业务确认”；本报告不把该声明本身当作缺陷，也不要求首期工作台先完成正式算薪、银行支付或税务接入。

## 3. 详细发现

### A-01 / P1：多项目候选编号与初始化作用域未定义

**证据：** PRD L98、L164–165要求创建评审项目并加载43+3个候选；L156要求沿用原编号；L182仅写“编号唯一”，未说明唯一范围。

**反例：** 同一租户建立甲、乙两个评审项目，均加载OV-01。若按租户全局编号去重，乙项目无法获得独立候选；若每项目生成新编号，则需明确“记录身份、项目内编号、原始候选编号”的区别，否则跨项目历史和导出无法稳定关联。

**源码佐证：** `sql/mysql/upgrade/20261010-hrm-requirements.sql` L3–13的唯一约束是`tenant_id + code`；`HrmPayrollRequirementServiceImpl.java` L88–89、L135–143按code判重、初始化。该文件完整路径见第4节。现有逻辑不能不加设计地满足多项目复用，此处不据此判定全仓库不存在其他扩展能力。

**影响：** WB-01、WB-02的基础对象身份不明确，可能串用评审状态、跳过初始化或改变原始编号。

**补齐建议：** 定义需求记录ID、项目ID、候选模板编号的关系，明确唯一性和初始化幂等键；说明来源跨项目复用还是项目内复用，旧数据如何归入项目，模板升级如何保留人工修改。

**新增验收：** 两个项目各初始化46项，再分别重复初始化；两边数量不变，修改甲项目OV-01不改变乙项目内容、确认和历史，原始编号均可追溯。

### A-02 / P1：共享来源变更与需求确认失效未形成统一规则

**证据：** PRD L168、L185允许来源复用并将映射作为确认条件；L197要求关键内容变更重新评审；L201只要求来源内容或接口版本变化后重新核验；L239又允许按消费场景维护转换规则。

**反例：** 两条已确认需求共用来源S。S的工时单位由分钟改为小时，或者字段映射汇总逻辑改变，需求正文未改。可以实现为仅将S置为待核验、两条需求仍已确认，也可以实现为两条需求均重新评审，当前条文不能决定哪种正确。

**影响：** 原有确认可能继续覆盖已变化的业务含义；WB-04、WB-05、WB-07和AC-09无法按统一标准验收。

**补齐建议：** 列出关键变更字段，区分供给状态变化与语义变化；明确需求确认绑定的来源/映射版本、受影响需求集合、自动失效或人工复核规则、通知与恢复责任。单纯“待提供”不应自动撤销已明确的功能确认，语义变更则须按确定的规则处理。

**新增验收：** 同一来源关联两需求，分别改变联系人、供给状态、字段类型/单位和转换规则，逐项检查来源核验状态、需求评审状态与历史版本，结果必须来自预先确定的规则表。

### A-03 / P1：实施范围、统计分母与基线发布条件存在歧义

**证据：** PRD L61使用“纳入实施”；L182–188的字段表没有独立范围取舍字段；L207–212定义确认率、处置率，但未定义“有效候选”，又称暂缓会改变统计范围；L260要求导出本期纳入、暂缓、异议；L262规定“有未确认需求时不得标为完整确认基线”。

**反例：** 46项中40项确认且纳入本期，6项经评审暂缓。确认率应为40/46还是40/40？暂缓若移出分母，处置率中的“已暂缓”是否也移出？6项暂缓是否导致本期40项永远无法发布完整基线？两种实现均可找到当前条文支持。

**影响：** 总览指标、范围承诺及发布门槛不可一致复算；已确认需求也未必等同于本期纳入。

**补齐建议：** 分开定义评审状态与范围决策，给出纳入、候选、暂缓、移除/作废的规则；为每个统计量明确集合和分子分母。发布校验应明确针对拟发布的实施集合，且保留被排除项与理由；未决问题按是否阻断发布分类。

**新增验收：** 对“40确认纳入+6暂缓”、新增1个异议、移除重复项和空项目给出固定期望分子分母、清单条数及允许发布状态，并验证历史版本不变。

### A-04 / P1：授权原则清楚，但项目内实际判定和拒绝场景不足

**证据：** PRD L87–94给出角色建议，L186要求本人确认，L266–267要求服务端分别授权；Q-04仍待决定谁确认、核验和发布。AC-14覆盖跨租户及真实薪资边界，未明确同租户跨评审项目操作及“能编辑但不能确认”的场景。

**反例：** 同租户中，拥有需求编辑权限、仅参加项目甲的用户，将请求中的projectId或需求ID换为项目乙；或者在保存请求中直接提交“已确认”。文档要求拒绝越权，但没有可直接用作测试预期的成员、动作和范围判定矩阵。

**源码佐证：** 需求控制器L23–24的save仅声明update权限，需求服务L83–86校验操作者等于提交的reviewerId。这证明存在可复用检查，并不等价于PRD要求的项目签字资格或独立确认权限；未运行接口，不认定当前系统已可被越权利用。

**影响：** 本人操作与有权签字可能混淆，项目隔离和新增确认权限容易仅在前端完成。

**补齐建议：** 在Q-04决议中补齐角色×动作×项目/组织范围矩阵；明确评审人分派权限、本人确认与业务授权的双重条件、来源核验权限、成员移除后的访问及历史签字显示规则。

**新增验收：** 同租户跨项目读取/修改/历史/导出、仅编辑账号直接确认、无发布权账号发布、移除成员继续请求，均由服务端按矩阵拒绝。允许路径也需配套正例。

### A-05 / P2：历史导出缺少关联对象冻结与权限裁剪后的完整性定义

**证据：** PRD L198规定发布版本不可覆盖；L255–262要求六表、快照一致、历史再次导出且排除无权数据；L303要求新编辑不改变旧导出。未明确范围快照是否冻结来源、映射、问题、责任人显示值和规则引用版本。

**反例：** 发布V1后，实际来源名称、映射或问题处理状态变化。只冻结需求行、重新读取当前来源也能保留“需求旧版本”，但六表已经不再是V1。另一场景是导出人能看需求却无权看其来源，如何同时满足“关联可追踪”和权限排除也没有约定。

**影响：** 历史文件可能漂移；权限裁剪可能生成无法解释的孤立关联或将局部文件误标为全量基线。

**补齐建议：** 明确快照对象图及一致性边界，历史重导出的业务内容固定、生成时间等元数据可变；规定受限关联的占位/剔除策略、计数口径、完整性标识及历史访问使用何时的授权。不要求为此规定具体数据库实现。

**新增验收：** V1发布后修改关联来源和问题再导出V1，业务字段不变；缩小导出人权限后再次导出，既不泄露受限字段，也不冒充完整基线。

### A-06 / P2：问题待办有字段要求，缺少可验收的闭环状态和阻断规则

**证据：** PRD L169、L187、L259要求期限、处理和复核；L192–203仅定义需求、来源、实施三种状态；AC-07主要检查提出异议/暂缓，没有问题关闭、驳回复核和重新打开场景。

**反例：** IT填入“已提供”作为处理意见，HR认为格式错误。该问题算未决、待复核还是已关闭？解决人能否自行关闭？存在阻断问题时能否发布范围版本？当前条文未决定。

**影响：** WB-06和未决问题统计只能做成信息记录，无法确定实际闭环和交付条件。

**补齐建议：** 给出最小问题状态、允许动作、处理人与复核人权限、关闭依据、重新打开和逾期计算口径；明确问题与需求/来源的关联以及发布阻断等级。

**新增验收：** 提交处理→复核驳回→补充→复核关闭→重新打开全过程留痕；用固定日期验证逾期筛选和不同状态下的未决数。

### A-07 / P2：不适用来源的确认条件和验收措辞不一致

**证据：** PRD L185、L195允许“映射或明确不适用理由”，L61却并列要求字段映射和来源负责人；AC-06（L299）将“缺少映射/依据”列为拒绝条件，没有不适用例外。

**反例：** 某纯导航类需求无需外部数据，填写“不适用：仅调整页面导航”并由有权人确认。按L195可通过；按AC-06字面应因无映射拒绝。是否仍需要虚构来源负责人也不明确。

**源码佐证：** 服务L78–85在CONFIRMED时仍要求sourceSystem、sourceOwnerId；L120–127允许带理由的N/A映射文本。这是既有模型的复用约束，不能用来替业务决定正确口径。

**影响：** 合法不适用需求被阻断，或用户用伪来源和任意负责人绕过必填。

**补齐建议：** 增加“适用/不适用”的条件必填表：适用时需来源、负责人和映射；不适用时需理由及确认责任，明确来源负责人是否豁免。同步修订成功标准和AC-06。

**新增验收：** 有效不适用理由、空理由、适用但缺映射、由适用切换为不适用四种情形，分别给出确认、来源统计及导出期望。
