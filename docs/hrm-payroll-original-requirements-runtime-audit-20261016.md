# HRM 薪酬原始需求运行审计与完善计划

审计日期：2026-10-16（北京时间）。审计代码基线：`775165171ac547929db712fce7e0119925e2d5fd`。审计对象为用户本次上传的原始PRD与HTML，以及本项目在Codex Cloud中的实际功能。**本轮只审计和取证，没有修复应用代码或向远端推送。**

## 1. 审计结论

**当前不能认定项目完全满足原始需求，不建议直接进行正式薪酬上线验收。** 项目已有真实保存、审批、版本、计算与权限能力，并非纯演示页面；但本次在真实MySQL、真实登录和带业务数据操作下，复现了写入/审批500、新库工资目录不完整、部门范围不生效、需求确认校验不足及移动端表单越界等问题。核心“配置→核算→审批→发放→工资条→成本”链路未跑通。

原PRD v0.1明确是**业务评审稿**，43项为候选功能，COL-01～03及部分流程、权限为正式实现建议，Q-01～19尚待确认。本次按这些候选功能和建议检查差距，不将其冒充业务已签字的合同基线。也不把没有完成验证的功能判定为没有实现。

此前“46项已补齐”、1095项HRM测试通过和19页打开成功的记录，不能作为完全满足需求的证据。本轮初始库中员工、工资表、员工工资、代发、税务政策、缴费政策、工时记录和工资条记录均为0，仅有43条初始化征集项及主体/预算等测试资料。**空页巡检未覆盖真实核算和发布。** 本轮重新建立虚构数据并实际操作后发现阻断；详细见[初始数据量](hrm-prd-audit-evidence/initial-database-counts.json)。

### 当前可确认的能力

- 真实登录、未登录/模拟令牌拒绝，以及原有菜单、主体和租户负向检查可运行。
- 征集项可以新增、修改、追踪版本、拒绝旧版本和重复编号，真实Excel可以下载并读出新增条目；浏览器新增后刷新仍存在。
- 公式输入10得到20，缺变量被拒；但审批500，不能作为正式可用公式链路通过。
- 城市缴费政策、员工基数经不同用户审批后，5000元基数的个人8%、单位16%分别得到400和800元。
- 标准工时制度可以独立批准；税务政策不能自审，居民工资样例税150元、奖金单独税1080元均与独立验算一致。
- 批次草稿可以创建；缺法定目录时核算被阻断。无冻结成本时指标返回未知、成本报表导出被拒，未用0伪造结果。
- 手机触控下，关闭侧栏并通过弹窗内部滚动后，可以新增需求、保存并刷新查到；固定720px布局仍需优化，未误判为保存功能完全失败。

这不等同于真实发放、银行回盘、工资条本人隔离、跨年更正或成本分摊已经验收通过。

## 3. 主要问题与建议

严重度含义：P0=阻断正式薪酬上线/验收；P1=首轮业务验收前解决；P2=体验、可维护性及审计证据完善。

### F-01 · P0：真实MySQL锁定SQL错误，工资配置及审批不可用

**复现：** 用真实管理员执行`POST /hrm/salary/option/create`；用不同用户执行`POST /hrm/payroll/formula/approve?id=1`；执行有效的`POST /hrm/payroll/grade-policy/create`。均返回业务响应`code=500`。浏览器进入“薪资公式”点击“审批”同样复现，不是脚本猜测。

实际SQL包含：

```sql
... WHERE deleted = 0 AND (code = ?) AND tenant_id = 1
FOR UPDATE ORDER BY id DESC LIMIT 1
```

以及：

```sql
... WHERE deleted = 0 AND tenant_id = 1 FOR UPDATE ORDER BY id ASC
```

MySQL报告`SQLSyntaxErrorException`。对应工资项Mapper锁定查询、公式审批及薪级创建中的有序锁定；需继续定位真实租户/SQL解析链路的重写点，不能只因H2通过而认定正确。

**影响：** PLAN-01/02及后续配置、有效版本、正式核算受阻。新建公式可试算20元，不代表能完成批准生效。

**建议：** 修正锁定SQL生成/方言处理并保持租户隔离、事务和行锁；补MySQL+真实租户插件集成测试，覆盖带排序、带LIMIT、单行与多行锁查询。禁止通过移除租户拦截或行锁“解决”。复测工资项新增、公式批准、薪级创建/批准，以及并发重复提交。

证据：`SETUP-03`、`PLAN-01/04`、[审批截图](hrm-prd-audit-evidence/formula-approval-error.png)、错误SQL文件。代码定位：[HrmSalaryOptionMapper](../yudao-module-hrm/src/main/java/cn/iocoder/yudao/module/hrm/dal/mysql/salary/config/HrmSalaryOptionMapper.java)、[BaseMapperX](../yudao-framework/yudao-spring-boot-starter-mybatis/src/main/java/cn/iocoder/yudao/framework/mybatis/core/mapper/BaseMapperX.java)。

### F-02 · P0：完整迁移后的基础薪资目录不足以支撑核算

实际执行正确的`PUT /hrm/salary/option/sync`后，只有7个受控补发/奖金/税费调整/新增扣除条目；缺普通根分类及完整法定工资项。同步前后结果见`SETUP-01/02`。没有可用分类时不能通过正常工资项新增入口补齐；该入口同时受F-01阻断。

创建了主体1、2026年10月的实际草稿`batchId=1`后，执行`POST /hrm/salary/month-record/compute?id=1`返回`1050810017`：**“必需工资项[个人社保]未启用或类别/加减类型错误，请检查工资项配置”**。

另对未加入审计目录夹具的独立全迁移新库`hrm_cloud_full_20261016_0754`再次查询，工资项模板也只有7条、根分类为0，见[新库目录证据](hrm-prd-audit-evidence/fresh-install-catalog.json)。这排除了本轮临时夹具导致目录缺失的可能。

这是“表/字段完整”无法发现的基础数据缺口；本轮没有将其修成正式样例工资，也没有伪造已核算/已付款记录。审批/回盘/工资条等下游不能据空页判定完成。

**建议：** 提供有版本、幂等、分类与法定项引用完整的基础目录迁移/初始化流程；每租户明确同步步骤并给出就绪清单。新建库与新租户均必须只用正式初始化/API即可创建工资分类、定薪并完成一笔普通工资核算，不能依赖审计人员手写SQL。

证据：`SETUP-02-after-sync`、`SETUP-04-manual-catalog-fixture`、`CALC-01/03`。相关：[现有运行说明](hrm-runtime-verification.md)。

### F-03 · P0验收门禁：部门数据权限未过滤同主体其他部门金额

复现步骤：

1. 准备主体1的两名员工：员工1属于部门103，员工2属于部门104；两者缴费基数都完成HR/财务审批。
2. 给只读角色配置`dataScope=2`、`dataScopeDeptIds=[103]`，角色仅保留所需查询菜单，并有主体READ授权。
3. 重新真实登录该只读用户，调用`GET /hrm/payroll/insurance-policy/preview?entityId=1&year=2026&month=10`。
4. 实际返回员工1、2，包含部门104员工的基数5000、个人400、单位800及比例。`GET /hrm/payroll/attendance/employees`也返回两人。

`SEC-03`额外读取角色接口，确认数据库中保存的确实是部门103范围，不是仅构造了未生效的请求。测试后已恢复隔离只读角色原配置。

PRD第7节建议复用租户/主体/部门权限，第9.2要求不能超范围访问；当前表现是**主体授权未与系统部门范围取交集**。如果业务决定“主体READ即授权整个主体”，必须在Q-12明确签署该权限语义并调整验收；在此之前不能宣称已满足部门隔离。

**建议：** 形成统一主体×部门×人员×操作的服务端范围策略，覆盖列表、明细、候选人员、汇总和导出；补相同主体不同部门、不同主体、不同租户与员工本人四类负向运行测试。验收门禁为：按确认口径，部门103用户不能得到部门104金额或通过汇总/导出推导该金额。

证据：`SEC-01/02/03`。代码定位：[缴费政策服务](../yudao-module-hrm/src/main/java/cn/iocoder/yudao/module/hrm/service/payroll/HrmPayrollInsurancePolicyService.java)、[主体服务](../yudao-module-hrm/src/main/java/cn/iocoder/yudao/module/hrm/service/payroll/HrmPayrollEntityService.java)。

### F-04 · P1：需求可在空映射、无效责任人的情况下被确认

在隔离需求`COL-202616`上提交`status=CONFIRMED`、`fieldMapping=""`、`sourceOwnerId=99999991`、`reviewerId=99999992`，其余来源、验收、依据非空。接口返回0，重新查询状态为CONFIRMED；数据库核对这两个用户ID均不存在。空字段不会因为页面选择器通常提供有效用户而得到服务端保护。

版本冲突、重复编号和历史留痕确实有效，但不足以保证PRD第2.1、4.3的真实负责人和字段确认质量。

**建议：** 确认时校验责任人存在、有效且有相应授权，要求必要映射或有依据的“不适用”；若评审负责人和实际确认人允许不同，需要显式区分委派与确认，防止名义负责人无效。来源负责人变更/账号禁用时重新进入待确认，保留旧历史，不覆盖既有审计事实。

证据：`REQ-05`及实际需求Excel/历史；[需求服务](../yudao-module-hrm/src/main/java/cn/iocoder/yudao/module/hrm/service/payroll/HrmPayrollRequirementServiceImpl.java)。

### F-05 · P1：部署文档同步地址错误，错误提示误导启用诊断

现有运行文档让部署者调用`PUT /hrm/salary-option/sync`，实测返回501和“HRM已禁用”。正确路径是`PUT /hrm/salary/option/sync`，在同一已启动服务内返回成功。不能把前一个响应解释为本轮根本没启用HRM。

**建议：** 校正文档、统一提供可执行初始化检查；未知HRM路径应与模块真实未启用区分。升级步骤要用自动化脚本对实际控制器路由做烟测，同时检查完整业务目录而非只检查表结构。

证据：`SETUP-02-documented-sync`与`SETUP-02-after-sync`，文档位置：[运行说明](hrm-runtime-verification.md)。

### F-06 · P2：原型“按模块征集”的上下文未保留

原型9个业务视图内均有功能点和依赖数据源的征集面板。当前运行页面采用独立“需求评审”集中页，19个检查页未看到模块内征集面板或对应编号的上下文入口；集中页可以按模块过滤，但业务人员需要自行对应。

这属于PRD产品目标/信息架构建议的差距，不要求照抄原型的示例图表、35%或样式；不能把它当成核心核算故障。

**建议：** 业务页增加轻量“本模块需求与来源”入口，自动带模块筛选和需求编号；征集清单反向定位业务页。DS-01～DS-12形成可复用来源目录，避免各需求仅填写互不关联的自由文本。是否必须保留内嵌面板由需求负责人确认。

证据：HTML9次`reqPanel`调用、[浏览器页面按钮/筛选观察](hrm-prd-audit-evidence/browser-results.json)。

### F-07 · P2：390px触控屏的需求表单超出视口，需额外滚动

在390×844、触控模式下，按正常菜单操作关闭侧栏遮罩后可以打开“新增需求”，但初始弹窗宽720px，保存按钮横坐标约644px，处于390px视口之外。补测发现浏览器可以通过弹窗内部滚动将保存按钮移入视口并触达，因此**不能据初始边界断言手机端无法保存**。补测还实际填写新增需求并保存，刷新后仍能查询到`COL-202620`。这是自适应布局与操作成本问题，应与功能完全不可用区分。

**建议：** 移动端使用自适应宽度/全屏抽屉、单列标签和固定可达操作区；检查日期选择器、金额表、宽表横滚及菜单遮罩。验收应使用真实触控模式完成新增→保存→刷新，而不是只拍一张窄屏截图。

证据：浏览器`mobile-requirement-form`的实际边界，[弹窗初始截图](hrm-prd-audit-evidence/mobile-dialog-initial.png)。定位：[需求页固定720px](../yudao-ui/yudao-ui-admin-vue3/src/views/hrm/payroll/requirement/index.vue)、[公共Dialog](../yudao-ui/yudao-ui-admin-vue3/src/components/Dialog/src/Dialog.vue)。

### F-08 · P1：缺少与原始需求相匹配的带数据端到端验收门禁

本轮34项相关H2测试全通过，同时MySQL创建/审批500；19页首次加载全部正常，同时实际审批按钮失败。初始验收库没有员工/工资/回盘/工资条。本轮无法证明工资到支付再到本人可见、成本分摊的完整结果。

**建议：** 将当前“已补齐”状态拆为“代码实现/自动回归/运行验收/业务签字”，已存在代码但未完成运行链路的点保持待验收；核心端到端失败必须阻断交付。既有完整回归记录保留，但不得继续作为每个功能已验收的替代证据。

### F-09 · P2：规则有效日期以数组返回，页面未按日期格式展示

实际`GET /hrm/payroll/formula/list`返回`effectiveFrom=[2026,1,1]`、`effectiveTo=[2026,12,31]`；浏览器公式表格显示为`2026,1,1`和`2026,12,31`，而不是统一日期格式。审批截图同时保留了这个显示结果。不能用TypeScript静态检查通过推断运行时日期契约正确。

**建议：** API响应DTO统一ISO日期，页面使用统一格式化器并校验日期选择器、复制版本、有效期比较和导入导出。当前已复现的是响应/显示不一致；未验证的编辑与比较路径不能据此直接判为失败。
