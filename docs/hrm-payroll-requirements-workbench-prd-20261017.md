## 1. 背景、来源与理解边界

### 1.1 用户原始诉求

用户于本次聊天粘贴的豆包对话记录标注日期为2026年9月29日，其中用户原话为：

> 人力资源系统当中，薪酬管理模块，结合相关的管理要素，例如考勤、加班、工时、社保公积金标准等，系统的制作出应用页面，以便以此为模版征集相应的功能需求和数据源需求

据此，本产品应让业务人员通过具体页面理解业务、提出需求，回答：需要什么功能、涉及什么字段、数据来自哪里、规则是什么、由谁提供和确认、如何验收。

### 1.3 当前问题

1. 单看文字清单，业务人员难以说明功能、字段和操作细节，需要可讨论的应用场景。
2. 功能与数据来源容易分开讨论，导致需求已确认，但数据无人提供、字段无法匹配。
3. 静态原型只能演示，评审意见、负责人和确认依据无法在原型中保存。
4. 当前系统已拆分多个配置、来源审批和业务页面，需要提供连贯的评审导航，降低理解成本。
5. 页面展示、业务需求确认、数据可用、功能实现和运行验收容易混淆，需要分别呈现。

## 2. 产品目标、成功标准与范围

### 2.1 产品目标

建立一套业务人员可以直接使用的薪酬需求评审工作台，完成：

- 看得懂：通过业务页面、字段、流程、示例理解薪酬全貌。
- 提得出：在具体模块、字段或操作旁补充需求、问题及规则。
- 找得到：每项需求能关联上游数据源和责任人，能返回对应页面。
- 确认清楚：功能范围、数据准备、未决问题分别记录。
- 交付明确：输出可追溯的功能清单、数据源清单、问题清单和实施范围版本。

### 2.2 首期成功标准

| 目标 | 可检查的结果 |
| --- | --- |
| 覆盖完整 | 十个评审视图可访问；43个原型功能点均有编号和页面映射；归档PRD补充的COL-01～03单独追踪 |
| 上下文明确 | 每条新增意见保留模块、页面及可选字段/操作锚点，能够返回原页面 |
| 数据责任明确 | 已确认需求均有验收条件；来源适用时填写实际来源、映射和来源负责人，不适用时按第7.4节豁免并由有权评审人确认理由 |
| 评审可信 | 确认人、时间、依据和版本可追溯；预置候选点默认待确认 |
| 可真实交付 | 保存刷新不丢失；导出可打开并与对应版本及筛选范围一致 |
| 展示易用 | 桌面和移动端完成浏览、提意见、保存和查看历史；不存在操作按钮超出视口而无法触达的情况 |

### 2.3 分阶段范围建议

| 阶段 | 范围 | 交付边界 |
| --- | --- | --- |
| A：需求征集工作台 | 十视图、关联管理要素、示例、页面内征集、来源盘点、评审历史和导出 | 优先验证需求征集闭环；不要求先准备真实员工和薪资才能评审 |
| B：正式需求基线 | 确认适用主体、人员、规则、来源、权限、范围及验收样例 | 由有权业务人员确认；未决项显式保留 |
| C：业务实施与验收 | 按基线接入数据、配置规则，核算、审批、发放、工资条及成本等 | 复用当前已开发能力，逐项核对验收，不重复建设已满足的功能 |

上述阶段用于组织交付，不据此删除当前系统的核算、冻结、回盘、税务等功能。阶段A的完成不替代阶段C的业务验收。

| --- | --- |

| 当前系统的真实业务操作 | 保持既有权限和入口，通过明确导航与评审展示区分 |

## 3. 用户角色与场景

| 角色 | 主要任务 | 建议权限 |
| --- | --- | --- |
| HR | 补充薪酬、人员、考勤、加班和缴费需求，说明规则与来源 | 编辑获授权范围的需求及业务说明 |
| 财务 | 明确税务、发放、成本和对账口径 | 评审相关需求、确认验收样例 |
| 业务主管 | 明确排班、认可工时、异常处理、绩效等业务场景 | 录入意见、确认授权事项 |
| IT/来源负责人 | 盘点实际系统、字段、接口、唯一键与更新频率 | 维护数据源、映射及可供给状态 |
| 需求负责人 | 整理候选范围、分派责任、组织评审、发布范围版本 | 汇总、版本发布和受控导出 |
| 系统管理员 | 配置用户、角色及访问范围 | 技术管理不自动赋予业务签字权 |

核心场景：

1. 评审前：负责人建立评审项目，选择适用组织、业务范围和参与人，加载候选需求与示例。
2. 评审中：参会者进入模块，对照页面提出功能、字段、规则及数据来源意见，分派责任人。
3. 来源盘点：IT补充实际系统、接口/文件、字段、匹配方式和缺口，业务确认数据含义。
4. 评审确认：有权人员确认功能范围、依据和验收条件；数据尚未准备完成时继续显示缺口。
5. 评审后：负责人导出带版本的清单，明确纳入、暂缓、有异议和待补证项，交研发实施。

员工自助使用属于后续业务场景。需求评审访问不应以账号已绑定员工档案为前提；当前 `/hrm/portal/opening-guide` 是员工端开通入口，不适合作为本工作台入口。

## 4. 信息架构与统一交互

### 4.1 一级导航

保留十个面向业务的评审视图：薪酬总览、薪酬方案、工资核算、个税与工资条、考勤、加班、工时、社保公积金、报表分析、需求征集总览。

当前实现可复用多个子页面，但评审导航应将它们归集到上述业务视图，并提供前后步骤指引、相关页面链接及返回原上下文功能。

### 4.2 业务页统一布局

1. 页头：模块名称、用途、评审范围、示例标记和前后业务步骤。
2. 业务展示区：流程、表格、表单、图表、关键字段和正常/异常示例。
3. 模块需求征集区：在页面内直接展示候选需求、处理状态和意见入口。
4. 数据源征集区：展示本模块依赖来源、必要字段、当前供给状态和责任人。
5. 问题区：展示未决规则、来源缺口和待办，支持查看历史及相关需求。

桌面上允许并排或上下排列，移动端按业务展示、需求、来源顺序堆叠。首次进入时应直接看到征集区及其用途说明；可折叠，但不能只依赖隐藏的链接或悬浮弹层才能理解征集内容。

### 4.3 页面内意见入口

- 模块级：“补充本模块需求”。
- 字段级：“这个字段从哪里来”“补充字段说明”。
- 操作级：“补充该操作的规则或例外”。
- 流程级：“补充审批角色、顺序或异常处理”。

上述入口进入同一需求记录流程，自动带入页面、模块和锚点。意见保存后可在页面内看到编号与摘要，并进入集中清单继续评审。

### 4.4 示例与实际数据

- 示例默认使用虚构人员、部门、期间与金额，持续展示“示例数据，仅用于讨论”。
- 示例展示与真实业务接口写入隔离；演示操作不调用付款、消息外发或正式业务提交接口。
- 同一示例员工在核算明细、工资条和汇总中使用一致数据；计算关系、单位和舍入说明可查看。
- 缺数据、部分失败、待确认、空结果、接口错误分别展示，避免用零或成功提示代替未知状态。
- 保留原始HTML作为参考；若新展示修正原型中的金额矛盾，应记录调整理由，不改写归档原件。

### 6.3 状态与确认规则

功能评审状态为：待确认、评审中、已确认、有异议。v0.3将“暂缓”统一归入独立范围决策，不再同时作为评审状态。

- 新增进入待确认；评审中用于补齐场景、规则和来源说明。
- 已确认须有功能说明、范围、验收条件、有效评审负责人和确认依据；来源字段按第7.4节条件必填。有权评审人本人执行确认，同时绑定第6.8节项目范围版本及第7.5节来源/映射版本。
- 有异议须有异议说明、责任人及下一步；范围暂缓须有原因及重新评估条件。
- 需求的场景、范围、规则、验收条件、来源适用性/关联或映射等语义内容变更，产生新版本并回到评审中。已确认的其他关键引用变化按第7.5节传播，旧确认保留在历史。
- 任命新评审负责人使当前已确认需求回到评审中；账号显示名变化或原签字人随后离职，不追溯抹除有效的历史签字。需再次确认时重新指定有效授权人员。
- 已发布范围版本不被后续编辑覆盖；变更形成下一个范围版本。
- 提交时校验记录版本；发生并发冲突，提示查看最新内容，保留本次输入以便合并。

一般编辑可将待确认置为评审中；提出异议可由REQ_EDIT在授权范围内执行，但已确认项提出新异议须产生新版本、取消当前确认有效性，原签字保留。确认只能由REQ_CONFIRM的当前分派人执行；一般保存即使提交已确认状态也须经过相同服务端授权和版本校验。评审人可按新依据重新确认有异议项，异议处理记录保留；范围纳入、暂缓均不能绕过这一过程。

数据准备拆为供给状态（未盘点、待提供、已提供、有问题）和语义核验状态（待核验、已核验、有问题）。来源关系只有已提供、当前来源语义/关系映射及范围适配核验通过、第7.6节两层质量证据元组匹配且无关联未决DATA_READINESS问题时，才显示“已核验可用”；其他组合显示供给状态及核验标记。“不适用”属于需求的来源适用性，按第7.4节单独处理。来源和映射变更按第7.5/7.6节重新核验，不能只改一个汇总标签。

实施状态作为独立信息：未排期、开发中、待验收、验收通过。界面不得从“需求已确认”自动推导为“已实现”或“已验收”。

### 6.4 范围决策、统计集合与发布资格

同一项目的需求采用以下独立范围决策，默认候选；仅有SCOPE_DECIDE授权的人员可以修改并留痕：

| 决策 | 含义及必填条件 | 对功能评审状态的影响 |
| --- | --- | --- |
| 候选 | 尚未决定是否在本期实施 | 不自动改状态 |
| 纳入本期 | 拟纳入实施；写明决定依据，允许先纳入再补齐评审 | 不自动确认，发布时仍须满足确认条件 |
| 暂缓 | 写明原因、责任人及重新评估条件 | 不自动确认或撤销确认 |
| 移除作废 | 重复、误录或超出项目边界；写明理由，重复项指向同项目保留项ID | 原内容/历史保留，不计有效集合；恢复为候选时回到评审中 |

定义：U＝项目全部需求（含移除项）；E＝U中未移除作废项；I＝E中纳入本期项；C＝E中当前需求语义与projectScopeVersion绑定均有效的已确认项；T＝E中暂缓项；D＝E中有异议项。I、T、候选互斥，C是独立评审维度。

| --- | --- |

| 范围处置率 | （\|I\|＋\|T\|）／\|E\|，不使用“已确认＋已暂缓”计算 |
| 本期确认率 | \|I∩C\|／\|I\| |
| 异议数 | \|D\|，附所属范围决策，不能自动从E排除 |
| 来源可用率 | L中可用关系数／\|L\|；L为E中适用需求的当前需求—来源关系集合，每个关系ID只计一次，暂缓项仍计入 |
| 本期来源可用率 | 对I使用相同的关系集合算法，独立显示 |

### 6.5 对象身份、初始化与既有数据归属（A-01）

- 项目拥有稳定projectId并归属唯一tenantId；需求拥有稳定requirementId并永久归属该项目。界面、历史、API与导出关联使用ID，编号仅用于展示和追踪。
- projectCode在租户内唯一；需求的项目内编号以（tenantId、projectId、code）唯一。甲、乙项目都可拥有OV-01，各有独立ID、内容版本和确认历史。
- 候选模板使用稳定templateItemId、originalCode（如OV-01）、templateVersion。43＋3共46项构成模板包；同一项目初始化幂等键为（tenantId、projectId、templateItemId），不包含模板版本，避免升级时重复建项。
- 首次初始化复制模板形成项目记录；第二次只补缺，人工修改、范围决策、历史和已移除项都不覆盖或重新激活。初始化操作在并发时仍受唯一性约束，项目新增编号使用CUSTOM-0001等项目内序列，不复用旧编号。
- 模板更新对已有项产生待比较建议；由编辑者显式采纳或保留原文，记录原/新模板版本与决定。采纳语义变更按第6.3节重新评审。模板新增项可按稳定模板ID补入，模板删除项只提示，不删除项目记录。
- 实际来源也归属单一项目，具有sourceId与稳定版本；项目内允许多对多复用，关系拥有relationId和独立mappingVersion。跨项目首期采用显式复制，要求原来源PROJECT_READ和目标项目SOURCE_EDIT同时通过，产生新ID且保留出处，不共享可变来源。副本核验待核验、供给未盘点，不继承核验结论或签字；甲来源更新不传播至乙副本。
- 旧版tenant_id＋code记录经增量迁移归入该租户专用“历史导入”项目，保留原ID、编号、版本和签字快照，不自动复制到其他项目；来源文本标为待盘点，不凭空认定来源可用。迁移可重入并输出数量/关系校验；未知旧“暂缓”映射为范围暂缓、功能评审中，缺失理由列迁移待补问题。历史确认标记保留，当前确认需满足新契约后才进入C；迁移不得替业务补签。具体生产迁移另行实施、备份及验证。

### 6.6 来源适用性与引用

每条需求明确选择“适用”或“不适用”，默认适用；第7.4节是唯一条件必填规则。适用需求可以关联多个本项目来源，关系记录该场景消费的字段集合与映射/转换规则。确认引用元组及变更传播见第7.5节。

### 6.7 问题闭环与发布阻断（A-06）

问题有稳定issueId、项目、关联需求/来源/关系ID、描述、责任人、独立复核人、dueDate、处理依据、状态和阻断类别。至少关联一个需求或来源；阻断类问题另需界定影响范围是全项目还是一组需求（来源问题可通过关系派生需求集合）。状态为待处理、处理中、待复核、已关闭。

| 动作 | 允许者及前置条件 | 结果 |
| --- | --- | --- |
| 创建与分派 | ISSUE_MANAGE；责任人和复核人为范围内有效成员，且二人不同 | 待处理，记录问题与期限 |
| 开始处理 | 被分派责任人且有ISSUE_HANDLE | 待处理→处理中 |
| 提交处理 | 被分派责任人；填写处理说明及依据，不能只填状态 | 处理中→待复核 |
| 驳回复核 | 被分派复核人且有ISSUE_REVIEW；写明原因 | 待复核→处理中，历史保留 |
| 复核关闭 | 同上；核对所关联的当前来源/需求版本，填写结论及关闭依据 | 待复核→已关闭；处理人不能自关 |
| 重新打开 | ISSUE_MANAGE或被分派复核人，写明新证据/复发原因 | 已关闭→待处理，保留原关闭记录，重新指定期限 |

待处理、处理中、待复核均为未决，已关闭才计入已解决；关闭问题不自动核验来源或确认需求，仍需各自有权人员执行对应动作。成员失效后由ISSUE_MANAGE重新分派，历史处理记录不抹除。

阻断类别：BASELINE_BLOCK（规则含义、范围、权限或验收条件不清，阻断需求基线）、DATA_READINESS（规格已明确但未供数/供数质量不符，阻断来源可用）、ADVISORY（建议，不阻断）。全项目未决BASELINE_BLOCK，或影响集合与I有交集的未决BASELINE_BLOCK，均阻断发布；仅影响T/候选且非全项目者在排除清单保留，不阻断I。未决DATA_READINESS使相关来源关系不可用，但不撤销功能确认；ADVISORY只计未决。分类或影响范围的降级/缩小须ISSUE_REVIEW的独立复核人批准、说明依据，不能由处理者自行消除阻断。

采用Asia/Shanghai日期，dueDate当天结束前不逾期；未决且当前日期大于dueDate才计逾期。待复核仍可能逾期；已关闭不计当前逾期，但保留曾逾期及关闭日期。重开必须重新确定期限，并保留前一个周期。固定验收日期2026-10-17：dueDate=10-16的待处理/处理中/待复核各计1未决且逾期，dueDate=10-17的不逾期，已关闭不计未决/当前逾期。

### 6.8 项目范围生命周期与需求范围绑定（R-01）

项目范围允许修订，但采用独立PROJECT_SCOPE_EDIT动作。项目归属租户及projectId不可变；projectScopeVersion从1递增。范围版本冻结主体ID集合、组织ID集合、人员类型/业务场景边界、评审所针对的计薪期间起止及这些范围的业务说明，不使用日后会漂移的“所有公司/本月”动态值。项目展示名称、描述排版为metadataVersion，不能夹带范围修改。

每条需求明确选择以下方式，初始为继承；确认时都保存解析后的范围快照，不能只保存一个会动态变化的引用：

| 需求范围方式 | 当前范围与确认规则 | 项目范围变化后的处理 |
| --- | --- | --- |
| 继承 | 当前适用范围解析为项目的当前范围版本；确认绑定projectScopeVersion及解析范围摘要 | 新项目范围重新解析，全部当前已确认项进入评审中 |
| 显式子集 | 保存明确的主体/组织/人员类型/期间子集；必须各维度包含于当前项目边界，并保存projectScopeVersion及摘要 | 重新校验子集；即使仍在新边界内，首期也保守要求重新确认；超出新边界则标记SCOPE_MISMATCH，禁止确认 |

范围修订须填写理由、前后值、预期旧版本，显示全部影响ID，执行者拥有PROJECT_SCOPE_EDIT、全项目读/管理范围且业务授权的组织/主体/期间上限覆盖旧新范围的并集。SCOPE_DECIDE仅决定需求是否本期实施，PROJECT_MEMBER_MANAGE仅管理成员，两者都不能代替此动作。修改普通项目保存请求中的范围字段，也须走同一服务端校验；无权者可提出建议，不能直接改范围。扩大项目边界不会自动给现有成员扩权，新主体的动作仍需有效业务授权。

范围修订一次性完成以下可观察结果：

1. 写入新projectScopeVersion和事件，保留旧范围；E中所有当前已确认项生成新需求语义版本并回到评审中。E中其他项保留待确认/评审中/有异议状态，但均重算范围适配标记；移除项历史不变，恢复时绑定新范围并重审。
2. I/T/候选决策和U/E/I条数不自动变化，不因不匹配而删除或自动缩小需求范围；SCOPE_MISMATCH项继续计入统计。修正显式子集或经授权调整范围后，才可重新确认。需移除时另走SCOPE_DECIDE并说明理由。
3. 全部当前来源关系的范围适配、语义核验置待核验；质量证据按第7.6节因projectScopeVersion变化失配，保留旧证据但不能用于当前可用状态。来源和交付版本本身不因项目范围修订递增。未被需求引用的来源在以后关联时也须按新范围核验。
4. 所有强制发布决议须按第8.3节重新出具适用于新projectScopeVersion的有效版本，旧决议仅保留旧范围的事实。重新确认需求先要求当前范围及授权矩阵决议有效；发布另需全部强制决议、当前确认与引用有效。不得靠新范围配旧授权继续确认或发布。
5. 向评审人、来源核验人、需求及项目负责人生成站内待办；确认、来源核验、问题关闭和发布均检查请求范围版本，若与修订并发则按提交先后串行化，旧版本请求拒绝。修订前已提交成功的发布保留旧快照，修订后的发布不得引用旧确认；后台传播未完成时冻结相关确认/发布，不能展示新范围配旧有效标记。

### 7.2 每个实际来源的记录要求

来源记录包括：名称、所属组织、业务负责人、技术联系人、获取方式、接口/文件规格引用、频率、截止时间、覆盖期间、数据量、唯一键、员工匹配方式、质量检查、可用状态及核验依据。

每个来源具有sourceId、semanticVersion、operationalVersion；每条需求—来源关系具有relationId、mappingVersion与消费字段集合。语义版本记录数据含义与接口契约；运营版本记录联系人及供给情况。实际供数以deliveryVersion标识，每次替换样例/交付内容时递增并保存内容摘要/受控引用；交付、规格、映射与项目范围分别参与第7.6节质量证据元组，不能只按deliveryVersion匹配质量结论。版本变更和状态的联动以第7.5/7.6节为准。

字段映射至少包括：页面字段、业务含义、来源字段、类型、单位、必填性、转换/汇总规则、空值、重复、跨期和异常处理。一个来源字段可被多个页面复用，每个消费场景的转换规则须明确。

征集阶段不收集账号口令、接口密钥、真实身份证、银行卡或真实工资明细；使用脱敏规格或虚构样例说明结构。实际敏感数据接入另行授权并走现有安全配置。

### 7.3 业务规则确认单

对计薪、扣款、工时、缴费、个税、分摊等规则，统一记录：适用范围、规则说明、参数及单位、生效区间、政策/制度出处、确认人、舍入顺序、例外、正常/异常样例及期望结果。

原型中的5000、21.75、8小时、1.5/2/3倍、城市基数和缴费比例仅作为讨论示例。新页面标明“待业务核定”，不自动升级为生产默认政策；本PRD不提供现行税法或劳动法适用结论。

### 7.4 来源适用性的条件必填（A-07）

| 条件 | 确认所需内容 | 可豁免字段 | 来源统计与导出 |
| --- | --- | --- | --- |
| 适用 | 实际来源记录、当前语义规格、该需求的字段映射、有效来源负责人；明确字段与转换规则，供数状态允许待提供 | 不豁免来源和映射 | 每个当前关系进入L；缺关系计缺口。导出关系ID、来源/映射版本及供给/核验状态 |
| 不适用 | 描述无需消费业务数据的原因、适用性依据，由具备REQ_CONFIRM且被分派的评审人本人确认 | 来源记录、来源负责人、字段映射均可空，不虚构来源或代填人员 | 不进入L；需求行及来源清单中的“不适用声明”行显示需求ID、理由、确认人/时间/版本，不伪造sourceId |

两种情况均需场景、范围、验收条件、有效评审负责人和确认依据。“N/A”“不适用”或空白本身不是有效理由；如“不适用：仅调整菜单导航，不读取业务字段”可以接受，是否事实适用由有权评审人确认。

适用→不适用须记录变更理由，旧关系/映射进入历史，当前关系失活；当前需求回到评审中。有效理由已填写的当前不适用声明立即排除L，但不计入C，待重新确认后才进入C。不适用→适用也回到评审中，未建关系时按缺口占位计入L。两种切换均不改旧范围版本或复制旧签字。草稿可保存不完整资料，确认动作必须按本表校验。

固定验收：有效不适用声明可在不填来源负责人/映射时确认；空理由可以保存草稿但不能确认，并按未明确来源缺口计入L；适用但缺映射不能确认；由适用切换为有效不适用时关系退出L、当前确认失效、旧关系仍可在原版本导出查到。

### 7.5 来源与映射变更传播（A-02）

需求确认记录绑定（tenantId、projectId、projectScopeVersion、解析后需求范围摘要、requirementId、需求语义版本、适用性、当前各sourceId＋semanticVersion、各relationId＋mappingVersion、规则引用版本、确认人/时间及当时的授权/适用决议证据）。联系人和供给operationalVersion不纳入语义签字元组。来源负责人身份仍按第7.4节检查有效性，负责人变更另按下表处理。新增项目范围绑定按第6.8节传播；当前决议变化对未来动作及历史记录的影响按第8.3节处理。

需求语义修订与一般运营更新分别记版本/事件，避免仅修改联系电话就被误认为更改确认内容。所有变更均留历史；“当前确认有效”必须依据版本元组与传播结果判断，不能只读一个旧状态字段。

| 变更 | 核验与供给状态 | 对当前已确认需求的影响 |
| --- | --- | --- |
| 技术联系人/联系方式或显示名称变化，业务含义不变 | 运营版本增加，保留语义核验和供给状态 | 不改变需求确认；更新责任待办和历史，旧快照显示原值 |
| 来源业务负责人更换 | 运营版本增加，语义核验置待核验；新负责人必须有项目授权并由其核验人员重新核验 | 保留功能确认；生成责任交接待办，完成前来源关系不可用 |
| 待提供/已提供、有问题、到货延期等供给变化 | 运营版本增加，语义核验不变；仅供给标签变化不重置匹配的质量证据，但交付版本替换使来源层及所有消费层质量失配；可用条件按第7.6节 | 不改变功能确认；DATA_READINESS问题按第6.7节记录 |
| 字段新增、删除、类型、单位、业务含义、唯一键、员工匹配、周期粒度或接口规格版本变化 | 来源语义版本增加；该来源当前语义核验置待核验，来源层及所有消费层质量证据失配，供给事实不变 | 对所有当前关联该来源的需求保守失效：已确认→评审中，生成新需求语义版本；即使正文没改也必须重审 |
| 某消费关系的字段映射、转换/汇总、空值、重复、跨期处理规则变化 | 该关系mappingVersion增加、该关系语义及消费层质量待核验；匹配的来源层质量及其他关系的核验保留 | 仅该关系所属需求已确认→评审中，生成新语义版本 |
| 需求新增/移除来源关系、适用性切换、引用的业务规则版本变化 | 关系或需求语义版本增加，对应核验按新版本重置 | 对该需求已确认→评审中；按新关系重新确认 |

无法确认是否改变业务含义时，按语义变化处理。首期不做“未消费新增字段可免重审”的推断；同一来源的任意契约变更均按上表影响全部当前关联需求。已经历史失活的关系和其他项目副本不在传播集合内。

保存来源/映射变更时，计算项目内受影响需求ID集合，并与版本递增、确认失效、核验重置和待办创建保持一次可观察的一致结果。确认、发布若与变更并发，服务端重新核对引用元组，拒绝旧版本，不允许在传播完成前用旧确认发布。来源字段只能由来源编辑授权修改；映射由需求编辑授权修改；两者均不能借变更请求代为确认需求。

每次传播在工作台内通知受影响需求的编辑责任人、评审负责人、来源负责人/核验人及项目负责人，附变更原因、前后版本及影响ID；首期使用站内待办，不自动外发邮件/短信。来源核验人核对规格/映射，评审人重新确认需求；源已确认但数据未提供时允许需求先重获确认，来源仍显示待提供。重新核验可用不能自动恢复需求确认，重新确认也不能自动恢复来源可用。

固定验收夹具：R1、R2已确认且共用S v1，两关系已核验、供给已提供，当前交付质量核验通过，无未决问题；每个子例从同一夹具重置。修改技术联系人后两需求及可用状态不变；供给改待提供后两需求仍已确认、来源可用关系由2/2变0/2；修改S单位/类型或接口版本后两需求均进入评审中、可用0/2；仅修改R1转换规则后R1重审且该关系待核验，R2仍已确认可用，整体可用1/2；替换交付数据但语义不变时两需求仍已确认、质量待核验、可用0/2；任一子例均不改已发布V1。

### 7.6 质量证据的层级、绑定与恢复（R-02）

语义核验确认“规格/映射是否表达了业务含义”，质量核验确认“这份交付按该规格/映射处理后是否满足要求”。两者独立执行、分别留证；点击语义核验通过不能复制旧质量结论。所有证据具有evidenceId、不可变版本、检查规则版本/摘要、样本引用/内容摘要、执行结果、操作者、时间及授权依据。

| 证据层级 | 必须绑定的元组 | 检查内容与复用界限 |
| --- | --- | --- |
| 来源层质量QS | （tenantId、projectId、projectScopeVersion、sourceId、semanticVersion、deliveryVersion、交付内容摘要、检查规则版本） | 按来源规格检查类型、单位、唯一键、人员匹配及范围/期间覆盖等；同来源各关系可复用同一完全匹配的通过结论 |
| 消费层质量QC | （QS证据ID/版本、relationId、mappingVersion、解析后需求范围摘要、消费检查规则版本） | 按该需求转换/汇总、空值、重复、跨期和预期结果检查；即使无需转换，也须对直接映射给出通过结论，不能省略此层 |

每条关系可用须满足：第6.3节供给和问题条件、当前项目/需求范围适配及来源/映射语义核验通过，QS与当前完整元组匹配且通过，QC引用该QS并匹配该关系当前映射和范围且通过。拒绝无证据、失败、旧版本或仅有“通过”标签的结果；未来确认的功能规格可以不依赖已到货样本，但来源可用必须满足这两层质量条件。

规格、交付、项目范围或来源层检查规则变化，旧QS留历史且与所有依赖QC一并不可用于当前；新QS通过后，各关系仍须形成引用新QS的QC，不能仅把旧QC改挂新证据。只改R1映射/消费检查规则时，来源QS和R2的QC完整元组不变，可继续复用；R1须重新执行QC。相同交付原始文件可以复用为检查输入，检查结果不能跨失配元组直接复用。质量规则版本改变本身按本条失效处理；涉及业务规格/映射变更时同时走第7.5节功能重审。

来源和消费质量操作均要求SOURCE_VERIFY及对应对象范围；完成后重新检查其元组仍为当前值。若与规格、映射、交付或范围修改并发，旧检查结果只能保存为历史，不能将当前标为可用。质量通过不自动关闭DATA_READINESS问题，不自动恢复需求确认；仍分别走问题复核及需求确认。

固定夹具D1不变、无未决问题、供给已提供，S v1被R1/R2使用且QS1、QC1、QC2均匹配通过；各子例独立重置，旧发布V1不变：

| 变更及恢复步骤 | 固定来源可用率和证据预期 |
| --- | --- |
| S单位分钟→小时，或字段类型变化 | semanticVersion递增、两需求重审；即使语义/映射核验重新通过，旧QS1/QC1/QC2仍失配，可用0/2 |
| 上例按新规格检查同一D1 | 若D1不满足新规格，QS失败仍0/2；若QS新版本通过但未形成新QC，仍0/2；新QC仅R1通过时1/2，R2也通过后2/2 |
| 仅R1转换/空值规则改变 | R1重审、QC1失配，R2保持确认且QS1/QC2继续匹配，可用1/2；只重新语义核验R1仍1/2；新QC1通过后2/2 |
| 仅项目范围变化 | 按第6.8节重审；QS/QC均失配，语义复核不能恢复可用，须对新范围重做两层质量 |

每步保存原evidenceId与绑定值，不能覆盖旧结果。上述可用率只描述来源准备，重获质量通过并不代替两需求的重新确认。

### 8.1 关联快照与历史导出（A-05）

- 每个发布范围版本拥有稳定releaseId、版本号、projectScopeVersion、创建人/时间、范围决策与统计规则版本；projectScopeVersion表示项目业务边界，releaseId表示某次发布的完整快照，两者分别管理。草稿导出也记录固定草稿快照ID，避免同一下载过程中内容漂移。
- 一致性边界覆盖项目当时名称和业务范围正文、projectScopeVersion、本项目U中的需求内容/语义版本/评审与范围状态、确认引用元组、关联的来源规格/供给/语义与质量核验版本及证据、关系与映射、规则说明/引用版本、问题/处理/复核、成员责任人的ID和当时显示名、页面上下文，以及所有边和排除理由。第8.3节全部强制决议、决议条款正文/摘要、批准时与发布时授权证据及各自当时状态也属于必须冻结的依赖对象，不能只存当前决议查询链接。
- 快照从同一一致状态生成；任一关联对象并发变更时，重试生成或明确拒绝，不能拼接不同时间的六张表。关联规则若来自外部文件，冻结其受控版本标识、内容摘要和评审所依赖的规则文本；外部链接失效不改变已冻结正文。
- 权限范围相同的用户重导出同一releaseId时，排序、业务字段、状态、显示名、关系、排除理由和统计不变；允许变化的仅为导出人、生成时间、任务ID及文件容器元数据，不要求二进制字节完全相同。后续改名、供数、关闭问题不覆盖旧快照。
- 历史读/导出一律使用请求时的有效租户、项目成员、动作及对象范围授权，不沿用发布时权限。被移除成员即使知道releaseId也不能下载；异步任务在生成及领取下载时再次校验，下载链接不能成为永久越权入口。
- 可见需求关联的受限来源/问题/人员信息，按每个可见需求将所有受限边合并成一个“受限关联-1”等导出内临时占位编号；不通过占位数透露实际隐藏对象数。只保留“关联内容受限”标记，隐藏真实ID、名称、字段、负责人和具体原因。六表中的关联表使用相同临时号且有占位行；全部不可见的需求行和其专属关联完全剔除。可见信息有其他允许路径时按该路径单独输出，不能据此补出受限边。受限决议/批准授权依据按第8.3节在版本说明中合并占位，不能借规则引用或需求依据文本透出受限内容。
- 有筛选或权限裁剪时标为“筛选节选”或“权限受限节选”，显示基于可见行重算的分子分母；不显示项目全量隐藏行数或原全量指标。完整性说明仅表示存在裁剪，不泄露隐藏对象详情。任何节选不得标为完整确认基线。适用但关联受限的需求，其可见来源统计按一个不可用缺口占位，不展示被隐藏的关系数量。
- 对某对象的内容权限变化，允许历史文件按当前权限裁剪，禁止用“旧版不变”绕过授权；除这种裁剪和明确的脱敏外，可见业务字段保持快照原值。服务器保留完整快照，用户无权修改它来制造完整性。

### 8.2 完整需求基线发布门槛（A-03）

只有同时满足以下条件，拥有BASELINE_PUBLISH的人员才可发布“本期完整确认需求基线”：

1. 项目非归档且I非空，发布人具备全项目U及其快照闭包（含决议、授权依据）的全量可见范围，生成过程不依赖权限裁剪。
2. I全部为当前有效已确认版本，第7.4节条件必填及第7.5节绑定元组均有效；均无SCOPE_MISMATCH，确认时绑定范围等于当前projectScopeVersion。已签字人后续离职不追溯撤销旧签字，未完成的重审必须由当前有效评审人执行。
3. 不存在第6.7节定义的相关未决BASELINE_BLOCK；DATA_READINESS、ADVISORY及未纳入候选的异议如实列出，不以需求基线名义保证数据已经可用。
4. 所有不纳入本期项均列排除清单及理由；候选必须写明本期不纳入原因及责任人，暂缓有重新评估条件，移除重复项有可追溯目标。
5. 项目实际范围、授权矩阵、状态/变更规则和输出格式已形成第8.3节定义的当前有效决议；适用范围绑定当前projectScopeVersion、批准权限可证明、条款覆盖完整；未签署的模板建议不能作为既定业务授权。影响基线的Q-01/02/04/05/07/10须有决议，其他未决项逐项分类为基线阻断、数据准备或建议。

供数待提供不自动阻断已确定规格的需求基线；若连字段含义、匹配或规则都未明确，则按未确认或BASELINE_BLOCK阻断。工作台自身正式研发基线也须先完成影响首期范围、权限和状态设计的实际决议；本文仍为待确认建议稿，不能自动满足本条。

发布检查和快照冻结基于同一版本校验；任何项目范围、需求、来源语义、权限或强制决议的版本/状态变化导致前置不满足时拒绝并返回可见的阻断原因。发布留操作人、依据、范围版本及幂等请求号，同请求重试返回原releaseId。后续变更形成下一版本，既有发布内容保留。

### 8.3 强制业务决议与批准授权证据闭包（R-03）

决议是独立发布依赖对象，不能由需求已确认标记或一般规则链接推定。每个对象具有decisionId、不可变decisionVersion、条款正文/内容摘要、覆盖Q编号和PRD条款版本、tenantId/projectId/projectScopeVersion、适用主体/组织/人员/期间、effectiveFrom/effectiveUntil、创建人、实际批准人及时间、批准时授权证据ID/版本、状态及状态事件序列。规则引用中如果使用decisionId，必须映射到该对象的确定版本，快照仍按本节完整冻结。

状态为草稿、待批准、有效、已撤销、已替代；未来生效/已到期由有效期计算。草稿提交待批准，拥有DECISION_APPROVE且非该版本起草人的被指定业务批准人执行批准，需条款覆盖和适用范围符合其授权。可提前批准，但到effectiveFrom前不能用于动作或发布。正文、适用范围、批准条件修改必须新建版本重走批准；批准后的原正文和签字不允许原地改写。

正式生效版本撤销或替代由DECISION_APPROVE授权人员执行，须给出原因和批准依据；事件追加留痕，生效替代版本与原版本失效应作为同一可观察切换。同一Q/条款在同一项目范围和时间不能有两个互相冲突的有效版本；发现重叠或覆盖缺失时拒绝新确认/发布，不由实现者自行择一。项目范围修订后旧决议不能用于新范围，按第6.8节另行批准。

批准授权证据至少冻结：grantId/版本、批准人ID及当时姓名、当时有效账号/项目成员状态、DECISION_APPROVE动作、组织/项目/期间范围及委派上限、授予人/时间、授权生效区间、授权依据的决议/签署材料受控版本与摘要。授权链追溯至租户预先登记的业务授权根记录，不能由正在批准的决议自身赋予批准权；初始根依据须由实际有权业务人员提供并登记，不能由系统或本PRD代签。发布人的BASELINE_PUBLISH资格也以同样结构冻结当时事实。根签署材料按受控副本保留所依赖正文和摘要，不能只留下可能变化的外部URL。

未来确认/发布选择同时满足覆盖当前范围和条款、批准完成、时间有效、未撤销/未替代的决议版本；旧决议或空链接不能通过发布。Q-04调整授权时，后续请求一律使用当前授权，撤销的权限立即拒绝，不沿用旧成员缓存。正常替代不抹除旧需求签字；若Q-05等决议改变具体规则或验收含义，按第6.3/7.5节使相关需求当前确认失效并重审。单纯换批准人/更新矩阵且业务含义未变时，旧签字保留当时有效依据，新动作使用新授权；涉嫌签字依据无效时由有权人员提出阻断问题，不能自动篡改历史。

每次发布必须冻结：本次使用的全部决议ID/版本、正文条款、当时状态、有效期与范围版本，批准事实及上述授权证据链，发布人授权事实，发布检查时间和判定结果。在“评审版本说明”工作表采用SUMMARY、DECISION、GRANT三种记录类型及稳定快照内关联号输出；无须第七表，功能需求/范围表的行数保持原口径。完整文件内所有决议/授权引用均可在该表解析，注明依据适用的Q/条款及项目范围；后续撤销/替代不改旧快照的“当时有效”状态。

同权限重导出V1使用当时冻结正文、审批状态及授权链，不能用当前D2覆盖当时D1；允许另列当前生命周期提示，但必须标“当前查询信息”并与冻结业务内容分开，不改旧发布判定。无权查看决议或授权依据时，版本说明将全部受限决议/授权边合并为一个临时“受限发布依据”占位，隐藏真实ID/版本、条款、批准人、摘要、数量和授权内容；各表关联到此占位。可见需求中的依据摘要也须一并裁剪，不能借自由文本引用泄露。文件标权限受限节选，不能冒充完整基线；发布动作要求完整闭包可见，裁剪仅用于历史或草稿读取/导出。

决议批准、撤销、替代、范围变更与发布须统一版本校验：若发布先提交，冻结其提交时仍有效的版本并保留；若决议变更先提交，旧发布请求拒绝并重取当前依赖。不得把D1的条款、D2的批准状态和D3的授权矩阵拼成一次成功发布。确认和质量核验也留各自操作时所用的决议与授权事实；其未来有效性分别按第6.8/7.5/7.6节判断。

固定验收：项目范围不变，Q-04决议D1和Q-05决议D2有效，其余强制决议及发布条件齐备，发布V1；随后分别修改草稿、批准替代版本、撤销或使决议到期。草稿不影响旧有效版本；替代/撤销/到期后V2必须使用当前有效且覆盖完整的决议，否则拒绝。V1重导出仍输出当时D1/D2正文、批准人、时间、授权依据及有效状态。Q-05替代改变业务含义时还须相关需求重审，单纯新有效决议不代替重审。并发、权限缩小按前两段给定结果验收。

### 9.1 项目动作授权矩阵（A-04，待业务签署的确定规则）

授权同时满足：有效账号＋同租户＋该项目当前有效成员＋独立动作权限＋该成员被授予的组织/模块/对象范围。服务端按目标对象反查所属项目，校验请求projectId一致；不能信任请求中的reviewerId、ownerId或任意来源ID。项目级列表/搜索按同规则过滤，历史、计数、导出与直接按ID读取均不例外，越权拒绝不得返回受限内容。

角色是动作集合的建议模板，可由业务签署后分派；多角色取允许动作并集，但仍受目标范围和第6.7节独立复核约束。下表“全项目”指该租户中的指定项目，不延伸到同租户其他项目。所有未显式授予动作默认拒绝。

| 动作权限 | 建议持有者 | 服务端判定范围与额外条件 |
| --- | --- | --- |
| PROJECT_READ | 所有评审成员 | 只读被授予模块/对象及其允许关联，历史同范围 |
| PROJECT_SCOPE_EDIT | 被指定项目范围负责人 | 全项目管理且业务授权覆盖旧新范围并集，按第6.8节改范围；不得由需求范围取舍或成员管理动作推导 |
| PROJECT_META_EDIT | 项目资料维护人员 | 只改展示名称/排版，不能夹带主体、组织、人员或期间修改 |

| ISSUE_MANAGE / ISSUE_HANDLE / ISSUE_REVIEW | 负责人 / 处理人 / 独立复核人 | 在授权关联对象范围内按第6.7节角色及当前分派执行 |

| DECISION_EDIT | 需求负责人/决议起草人员 | 在授权项目内建立决议草稿/提交，不得原地改已批准正文或自造生效状态 |

项目建立需要租户级PROJECT_CREATE授权，创建人不自动获得业务确认/发布权。首次项目授权管理员及委派上限由租户业务授权决议登记；后续授权变更留痕。技术超级管理员没有显式业务授权时也不能借管理权限签署、核验或发布。

PROJECT_CREATE还要求初始范围在其被授予的业务边界内；成员、范围、决议三个动作分别检查，任何组合角色仍不得跨越第8.3节既有授权根和委派上限。成员读范围需显式包含决议/授权证据对象才可查看其内容，通用需求读权不自动扩为决议证据读权。

范围较小的人员访问跨模块共享来源时，需要来源的显式对象读授权；能读需求不自动获得来源读权，裁剪按第8.1节处理。只有对来源及全部当前关联需求具备管理覆盖的人员可直接提交语义变更；覆盖不足时提交变更提议交负责人处理，避免局部权限修改影响其他范围。

成员移除/停用后撤销后续读取、修改、确认、历史与导出，正在运行任务在结果交付前再次校验；已完成历史签字保留当时ID/姓名/授权依据，仅向当前有读权者展示。未决任务重新分派，不把旧签字改成新成员签字。

### 9.2 持久化与性能执行要求

实施验收在第9节规定负载下，预热2分钟、连续运行10分钟，10个并发有效成员执行列表/保存；列表与保存各至少500个有效样本，分别计算P95≤2秒，预期成功请求非预期失败率为0。预设越权/冲突负例单独计数，不混入成功延迟样本；所有超时都记为失败，不从统计中删除。

同一负载期间执行20次六表全量导出，每次从提交到可下载≤30秒且文件内容正确、非预期失败数0；未达到样本数则结果标为未完成。记录硬件/软件、网络、数据规模、采样算法（nearest-rank）、各动作样本数、持续时间、P95、最大值、失败率和导出时长。此为待业务确认的测试目标，不是本次执行结果。

持久化测试使用两台独立浏览器会话：保存需求/映射/问题后刷新、退出并重新登录、另一个授权成员读取，值及版本一致；制造一次网络保存失败后保留编辑输入，重试仍受版本校验，不能以本地缓存冒充后端保存成功。

## 12. 实施顺序与待确认事项
